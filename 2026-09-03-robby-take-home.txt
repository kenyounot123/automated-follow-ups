⏺ Plan written. The shape of it:

  The load-bearing idea is that Quote#recompute_from_events! rebuilds the
  projection with a single aggregate query over the event log rather than
  folding each incoming event into current state. Aggregates don't care about
  insertion order, so idempotency and order-independence both fall out for free
  instead of needing ordering logic scattered through the ingestion path. Status
  becomes derived (accepted if any acceptance event exists) rather than
  last-write-wins, which is what keeps Q-1004 from being resurrected by its two
  post-acceptance views.

  Three things I decided and flagged rather than asked about:

  - last_contact_at conflicts with the event log on 23 of 30 quotes, in both
    directions. I'm treating it as max(snapshot, derived) on the theory that the
    snapshot records out-of-band contact (a phone call that emitted no event)
    while events record what the system saw. Neither is authoritative alone. If
    that field is meant to be pure derived state, this is the assumption to
    overturn.
  - Quotes where the customer replied and nobody answered get their own Needs 
    human reply section instead of an auto-draft. Sending a templated nudge to
    someone who just wrote you a real message is worse than sending nothing.
  - Quiet hours gate approval, not drafting, since a human pushes the send
    button anyway.

  One correction to my own earlier framing: I had conflated rate limiting with
  uniqueness in the sent_on index. Your split is right and I've built the plan
  around it - indexes enforce structural uniqueness, the cadence holds temporal
  rules, so tuning a cooldown doesn't require a migration.

  The README section on additional signals calls out opt-out/STOP keyword
  suppression as a TCPA compliance requirement that belongs next to the send
  guardrail rather than in the policy - worth noting as the one item on that
  list that would be a real bug to omit in production.

     Automated Follow-Up MVP

     Context

     Take-home build: a Rails app that ingests quote lifecycle events, triages
     which open quotes
     deserve a follow-up, drafts the message with a mocked LLM, and puts it in
     front of a human to
     approve or deny. Sending is human-triggered by Approve, never automatic.

     The repo is a bare Rails 8.1.3.1 / Ruby 3.4.9 skeleton (SQLite, SolidQueue,
     Turbo, Tailwind,
     importmap, Minitest + Capybara). No models, migrations, or routes exist.
     Two seed files are
     already present and they drive the design:

     - db/seed/quotes.json - 30 quotes, 27 open / 2 accepted / 1 dismissed, $420
       to $22,000
     - db/seed/events.jsonl - 88 lines, 5 event types, 2026-08-01 to 2026-08-16

     Five properties of that data set the requirements. Each has a test.

     1. 88 lines, 82 distinct event_ids. Six ids repeat, byte-identical.
        Ingestion must be
        idempotent, and a unique index is sufficient.
     2. Q-1004 is accepted at 08-10 but viewed at 08-11 and 08-14. Late events
        must not
        resurrect a terminal quote.
     3. Q-1017 is accepted in quotes.json with no quote_accepted event anywhere.
        The only
        acceptance event in the file is Q-1004's. Q-1017 is also the
        joint-largest quote at $22,000
        with two views, so any rule that derives acceptance only from events
        puts an already-won
        deal at the top of the follow-up queue. Acceptance must come from either
        source.
     4. Karen Nguyen owns Q-1003 and Q-1025 on one phone. Customer is a real
        entity.
     5. last_contact_at disagrees with the event log on 23 of 30 quotes, in both
        directions.
        Some quotes carry a contact time with no matching event (a phone call
        that emitted nothing);
        some have events newer than the snapshot. Neither source dominates.

     Also verified: quote_sent.timestamp == created_at for all 30 quotes, and
     every event
     references a known quote.

     Why: was Cadence::FollowUpMessage; the namespace already says follow-up.

     Draft, because the record outlives that status.
     ────────────────────────────────────────

     Why: was FollowUpPolicy. Triage means ranking by urgency under scarce

     us",
     which stays true when the source is a CRM instead of a seed file.

     Statuses use the words in the ask: draft, approved, sent, denied, failed.
     Reasons: viewed_no_reply, big_quote_stale, never_viewed, going_cold, plus
     needs_reply

     Approach

     Time: pinned demo clock

     Seed timestamps load verbatim. config.x.demo_now = Time.utc(2026, 8, 17),
     eight hours after
     the last seed event. Clock.now returns it, falling back to Time.current.
     Triage takes an
     explicit now: so tests pin it. The layout shows a demo-clock banner.

     With a frozen clock the recurring job returns an identical result on every
     tick, so the demo
     drives drafting from a button. The recurring entry stays as three lines of
     config showing the
     production path.

     Models

     Account, Customer, Quote, Event, Cadence, Cadence::Step, Cadence::Message,
     plus plain-Ruby Triage and Drafter. Logic in models; jobs and controllers
     thin.

     Cadence holds tunable rules: min_amount_cents, max_age_days,
     viewed_recently_hours,
     big_quote_amount_cents, stale_contact_days, active.
     Cadence::Step holds position, delay_hours, channel, prompt_template, label.
     Cadence::Message belongs to quote, customer and step, with status, reason,
     score,
     body and *_at stamps.

     Quote stores quoted_at, reported_last_contact_at, reported_status, plus
     signals
     rebuilt from events: last_viewed_at, view_count, last_customer_reply_at,
     last_outbound_at, outbound_count, accepted_at.

     effective_last_contact_at is the max of the reported snapshot and the
     derived contact times,
     because the snapshot records contact the system never saw and events record
     what it did.

     Ingestion: idempotent and order independent

     Event.ingest!(rows): insert_all with unique_by: [:account_id, 
     :external_event_id]
     ignoring conflicts, then recompute signals for every touched quote.

     Quote#recompute_signals! is a full rebuild from the event log - one
     aggregate query of
     MIN/MAX/COUNT over that quote's events, not an incremental fold of the
     incoming row.
     Aggregates are insensitive to insertion order, so idempotency and order
     independence both fall
     out for free. This is the core of the design.

     Duplicate event_ids are first-write-wins, documented as such. The seed's
     six duplicates
     are byte-identical so the distinction is invisible here; detecting
     conflicting payloads for the
     same id would be machinery for data that does not exist.

     Status is derived and terminal states are sticky:

     accepted   if accepted_at.present? (quote_accepted event) OR
     reported_status == "accepted"
     dismissed  elsif reported_status == "dismissed"
     open       otherwise

     Acceptance from either source, because Q-1017 is accepted with no event and
     Q-1004 has the
     event. No later event of any kind can move a quote out of a terminal state,
     which covers the
     post-acceptance views on both Q-1004 and Q-1009.

     Events naming an unknown quote are logged and skipped. The seed has none,
     and a nullable FK
     plus adoption callback would be machinery for a case that does not occur.

     Sends become events

     DeliverMessageJob writes a message_sent Event with a deterministic
     external_event_id of "cadence-message-#{message.id}", then recomputes the
     quote's signals.

     This is load-bearing rather than tidiness. Outbound history has exactly one
     source of truth,
     so the cadence sees our own sends the same way it sees the six pre-existing
     message_sent
     events; step position and timing stay correct after an approval instead of
     going stale. The
     deterministic id makes redelivery under retry_on idempotent for free.

     Triage: read-only

     Triage.new(cadence, now:).candidates returns ranked Candidate values and
     writes nothing.

     Next step and timing. Touches already spent equal outbound_count, so
     next_step = cadence.steps.find_by(position: quote.outbound_count + 1). The
     step is due when
     now - (last_outbound_at || quoted_at) >= next_step.delay_hours.
     Cadence::Step#delay_hours
     is the only timing rule; the cadence-level cooldown_hours from the earlier
     draft is dropped
     because two timing knobs governing the same decision is one too many.

     Suppression, all must pass: status open; amount_cents >= min_amount_cents
     (drops the two
     $420 quotes); age within max_age_days; a next_step exists (else the cadence
     is exhausted);
     the step is due; no draft or sent message already for that step; and the
     customer has not replied
     more recently than our last outbound.

     A customer with two open quotes gets one follow-up for each; that is
     intended. The per-step
     index still makes it impossible for either quote's message to go out twice.

     Reasons, first match wins:

     - viewed_no_reply - viewed within viewed_recently_hours, no reply, no
       outbound since
     - big_quote_stale - at or above big_quote_amount_cents, no contact in
       stale_contact_days
     - never_viewed - sent over 24h ago with zero views; likely bad contact
       details, so the copy resends the link
     - going_cold - open, no contact in N days, below the big-quote threshold

     Score, pinned so the ordering test is meaningful rather than
     implementation-defined:

     WEIGHT = { viewed_no_reply: 100, big_quote_stale: 80, never_viewed: 60,
     going_cold: 40 }
     amount_factor = Math.log10(amount_cents / 100.0)            # $420 -> 2.62,
     $22k -> 4.34
     recency_decay = 1.0 / (1.0 + days_since_last_signal / 7.0)  # last_signal =
     max(viewed, contact, quoted)
     view_bonus    = [1.0 + 0.15 * [view_count - 1, 0].max, 1.5].min
     score         = (WEIGHT[reason] * amount_factor * recency_decay *
     view_bonus).round(2)

     Sorted by score descending, ties broken by external_id ascending so the
     order is total and
     reproducible. Repeat viewing is a multiplier rather than a fifth reason,
     keeping one place that
     decides urgency.

     Quotes where the customer replied and nobody answered are surfaced under
     needs_reply
     instead of drafted (Q-1002, Q-1015, Q-1019, Q-1020).

     Drafting

     Drafter#draft(quote:, step:, reason:) interpolates the step's
     prompt_template with
     reason-specific phrasing, varied by an RNG seeded on quote.external_id so
     output is stable and
     assertable. No network. config.x.drafter names the class - the whole seam
     for a real LLM.

     Guardrails in the database

     - events (account_id, external_event_id) unique - idempotent ingestion
     - cadence_messages (quote_id) WHERE status = 'draft' partial unique - one
       pending draft per quote
     - cadence_messages (customer_id, quote_id, cadence_step_id) WHERE status IN
       ('approved','sent')
       partial unique - one message per step per quote per customer
     - cadences (account_id) WHERE active partial unique - one active cadence
       per account

       customers (account_id, phone) unique

       FKs throughout

     tunable without a
     migration.

     partial unique index

     def approve!

     Clock.now)

       DeliverMessageJob.perform_later(self)
       true
     end

  And the short version, plainly:

  An event comes in as a small record - which quote, what happened, when. A
  batch of them goes to a background job so nobody waits on it.

  The job does four things:

  1. Looks up which quote each row belongs to. If it names a quote we've never
     seen, that row gets written to the log and thrown away. Better than
     guessing a quote into existence.
  2. Puts the whole batch in with one insert. The database has a rule that says
     an event id can only appear once per account, so anything we already have
     just doesn't go in. That's the whole duplicate defence - it's in the
     database, not in code I could forget to write.
  3. Recounts each affected quote from scratch. Not "add one to the view
     counter." It asks the quote's entire history: when was it last viewed, how
     many views, last reply, last message we sent, was it accepted. Every time.
  4. Settles the status and kicks off the sweep that re-ranks quotes and writes
     drafts.

  Step 3 is the whole trick. Because it asks for a latest and a total over
  everything, the order the rows arrived in can't affect the answer. An event
  that shows up three days late just slots into the history and the numbers come
  out the same. There's no ordering logic anywhere because there doesn't need
  to be any.

  So: send the file twice, get 82 events both times. Shuffle it five ways, get
  identical numbers five times. Both of those are tests, not claims.

  The page also shows the two rows in the real data that forced design decisions
  - the $22,000 quote that's marked accepted with no acceptance event anywhere,
  and the one that got viewed twice after it was already won.
